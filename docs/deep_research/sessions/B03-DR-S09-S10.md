## 1. 唯一目标

在 B01 领域合同和 B02 durable runtime kernel 之上，建立一个完全离线、确定性、可恢复的执行策略层，并用 Fake Provider / Fake Tools 证明以下场景可以有界运行和完整重放：

1. success；
2. insufficient-evidence / abstain；
3. transient failure 后有限 retry 成功；
4. timeout 后按策略终止或有限 retry；
5. cancel 在安全边界生效；
6. budget exhaustion fail closed；
7. 单次 controlled replan 后成功或安全终止；
8. 任意已提交边界中断后 resume，不重复本地扣费、不重复已确认完成的 fake side effect；
9. 外部结果处于 unknown outcome 时不虚构 exactly-once。

本轮完成的是“可靠执行策略 + 确定性测试台”，不是生产 Agent、真实模型适配或真实研究能力。

## 5. 核心边界

### 5.1 策略层不拥有领域事实

策略层只决定：

- 是否允许发起下一次尝试；
- 是否超过预算或 deadline；
- 某错误是否允许 retry；
- cancel 是否已请求；
- 是否允许一次 bounded replan；
- 如何记录 attempt 和 outcome。

它不得：

- 生成或伪造 Source/Evidence/Claim/Citation 身份；
- 绕过 BriefApproval；
- 放宽 grounding/quote validator；
- 将 fake response 当作真实研究证据。

### 5.2 所有外部边界都必须可替换

Fake E2E 使用明确 Protocol/ABC 边界：

- `Provider`；
- `Tool` 或 `ToolRegistry`；
- `Clock`；
- 可选 `Sleeper` / deadline controller；
- cancellation signal。

本轮只能提供 Fake 和标准库实现，不提供智谱、DeepSeek、OpenAI 或其他真实 provider adapter。

### 5.3 不宣称 exactly-once 外部调用

系统可以保证：

- 一个已确认 committed 的 operation 不被本地 resume 再次执行；
- ledger charge 使用稳定 operation/attempt identity 去重；
- durable event/replay 可恢复本地已知事实。

系统不能仅凭本地日志保证：

- 请求发送后连接断开时，外部 provider 是否已经完成；
- 无幂等 API 的工具是否产生了真实副作用。

必须显式建模 `unknown outcome`，并默认 fail closed 或要求人工决策；不得自动盲重试非幂等副作用。

## 6. Error Taxonomy v1

实现结构化、严格、可序列化的错误分类，至少区分：

- `transient_provider`：短暂服务错误，可能允许 retry；
- `rate_limited`：受限流，可能允许 retry/backoff；
- `operation_timeout`：单次操作 deadline 到期；
- `run_deadline_exceeded`：全局 deadline 到期；
- `budget_exhausted`：任何硬预算不足；
- `cancelled`：用户/控制面取消；
- `contract_invalid`：schema/identity/ref 不合法；
- `grounding_rejected`：确定性证据验证失败；
- `permanent_provider`：确定性不可重试 provider 错误；
- `tool_failure`：工具错误，需标明 retry safety；
- `unknown_outcome`：调用是否产生外部结果不可知；
- `internal_invariant_violation`：程序不变量破坏。

精确枚举名可按现有代码风格调整，但每类必须冻结：

- retryable 与否；
- 是否计入 provider/tool call；
- 是否计入 token/cost（若可获得）；
- 是否可触发 replan；
- 推荐终态/结构化 reason；
- 是否允许自动恢复。

不得通过字符串包含关系判断 retry；必须使用枚举/判别合同。

## 7. BudgetSpec 与 BudgetLedger

### 7.1 BudgetSpec

实现不可变、版本化的硬预算合同，至少支持：

- 最大 provider attempts/calls；
- 最大 tool attempts/calls；
- 最大 input tokens；
- 最大 output tokens；
- 最大 total tokens；
- 最大 retry 次数或每 operation 最大 attempts；
- 最大 replan 次数；
- run deadline；
- operation timeout；
- 可选已知费用上限，但不能用二进制浮点直接累计货币。

预算必须是运行开始前确定的输入。运行中只能收紧，不得静默扩大。

### 7.2 BudgetLedger

实现不可变或事件派生、单调累积的 ledger，至少记录：

- provider/tool attempted、succeeded、failed；
- input/output/total tokens；
- retries；
- replans；
- elapsed/deadline 消耗或可验证时间点；
- 已知费用（如本轮 Fake 提供）；
- 每次 charge 对应的稳定 operation ID 与 attempt ID。

要求：

- 任何计数不得为负；
- consumed 不得减少；
- 同一 charge/attempt 重放不得二次扣费；
- retry attempt 真实计入 call、token、时间和成本；
- timeout/失败 attempt 若已经发出调用，也计入 call；
- replay 从 durable events 重建 ledger；
- ledger 不能只存在内存或 checkpoint；
- budget check 在发起调用前执行；
- 如真实 usage 只能在响应后获得，必须有 reserve → reconcile 或等价保守策略；
- 不允许先超额调用、再记录 `budget_exhausted`。

### 7.3 费用表示

如实现费用，使用整数最小单位或 `Decimal` 的规范字符串；禁止 `float` 累加后宣称精确成本。本轮 Fake price table 必须固定、显式且仅用于测试，不宣称是真实厂商价格。

## 8. Clock、Deadline 与 Timeout

实现注入式时钟：

- 生产策略使用 `time.monotonic()` 或等价单调时钟判断 deadline；
- Fake E2E 使用可手动推进的 `FakeClock`；
- 审计 UTC timestamp 与 deadline 计算分离；
- 测试不得依赖真实长时间 `sleep`。

至少支持：

- run-level absolute monotonic deadline；
- per-operation timeout；
- retry/backoff 后剩余全局时间检查；
- operation timeout 不得超过 run remaining time；
- deadline 到期后禁止新调用；
- timeout 与取消同时发生时，优先级必须文档化并测试。

如果使用 `asyncio.wait_for` / `asyncio.timeout`，必须测试取消传播和资源清理。不得通过后台遗留 task 继续消费 Fake 调用。

本轮不声称可以强杀任意阻塞同步第三方 SDK；真实 adapter 如何把 deadline 传递给客户端留到后续 provider batch。

## 9. Cancellation

实现轻量 cancellation signal/token，并在安全点检查：

- 发起 provider/tool 前；
- 一次 attempt 返回后；
- retry/backoff 前后；
- replan 前；
- validation/terminal transition 前。

要求：

- cancel 是幂等请求；
- cancel 后不得再发起新调用；
- cancel 不回滚已经 durable committed 的事实；
- cancel outcome 通过现有失败终态的结构化 reason，或显式版本化的新终态表达；
- 不允许为了增加 `CANCELLED` 状态而破坏 B02 v1 replay；
- cancel 与已完成终态竞争时，采用“第一个 durable terminal event 胜出”或其他明确规则，并测试。

本轮不实现 UI/API cancel endpoint。

## 10. Retry Policy

实现显式、版本化 retry policy：

- 最大 attempts 明确且有限；
- 仅对白名单错误类别 retry；
- contract、grounding、cancel、budget、permanent、invariant 错误不得 retry；
- 非幂等工具 unknown outcome 默认不得自动 retry；
- 每个 retry 都使用新的 attempt ID，但共享 operation ID；
- retry delay 采用确定性计算；v1 默认无随机 jitter，或使用显式注入的确定性 jitter source；
- backoff 前重新检查 cancel、budget 和全局 deadline；
- retry 不得递归无界调用；
- 所有 attempt 与决策进入 durable event/ledger，可 replay 且 replay 不重新 sleep/call。

Fake E2E 至少验证：

- transient → success；
- transient 直到 attempts 耗尽；
- permanent 不 retry；
- timeout 在策略允许时有限 retry；
- cancel 阻止 retry；
- budget 不足阻止 retry；
- unknown non-idempotent outcome 不 retry。

## 11. Controlled Replan Policy

本轮只实现 bounded replan 的控制合同与 Fake scenario，不实现真实 Planner。

至少表达：

- replan reason；
- triggering operation/error/evidence gap；
- old plan/subtask DAG identity；
- proposed new plan identity；
- replan ordinal；
- remaining budget；
- admission decision；
- rejected reason。

约束：

- 默认 `max_replans` 很小且来自 BudgetSpec；
- 新计划必须继续通过 B01 Subtask DAG 和引用校验；
- 不得修改已完成 subtask 的历史；
- 不得删除已获得 Evidence；
- 相同计划/无语义变化的 replan 被拒绝；
- replan 必须消耗 ledger 配额；
- replan 不能重置 retry、token、cost 或 deadline；
- 超过上限后安全终止；
- Fake replan proposal 是预编排脚本，不代表模型规划能力。

如 B02 事件只支持状态转换，需以显式版本化的 control event 扩展方式实现；不得用无理由 self-transition 规避 guard。

## 12. Operation Journal 与 Resume Safety

为每个 provider/tool 操作定义稳定身份和状态，至少区分：

- planned/reserved；
- started/dispatched；
- succeeded；
- failed-known；
- outcome-unknown；
- cancelled-before-dispatch。

命名可调整，但必须回答：恢复后这一 operation 是否允许再次执行？

规则：

- 已 durable succeeded：不得重执行；
- cancelled-before-dispatch：不得计为已调用；
- known retryable failure：可依据 policy 进入下一 attempt；
- outcome-unknown + 非幂等操作：不得自动重执行；
- outcome-unknown + 明确 provider/tool idempotency key：只有在 adapter contract 明确保证时才可重试；Fake 可模拟但不得外推到真实 provider；
- replay 只重建 journal/ledger，不执行 side effect。

事件写入顺序必须文档化，尤其是 dispatch 前后 crash window。不得宣称本轮解决分布式 exactly-once。

## 13. Provider 与 Tool 协议

定义最小 async Protocol/ABC，要求：

- request/operation identity 显式传入；
- timeout/deadline 可传递；
- 返回结构化 usage；
- 返回结构化 outcome 或抛出可映射 taxonomy 的异常；
- tool 声明 `read_only` / `idempotent` / `side_effecting` 等 retry safety；
- 不接受任意 raw dict 作为长期稳定合同。

本轮不要求完整 OpenAI-compatible schema，也不添加厂商字段。Provider 请求只需支持 Fake E2E 的最小文本/结构化响应。

## 14. Deterministic Fake Provider / Fake Tools

### 14.1 Fake Provider

实现脚本化 Fake Provider：

- 输入为预注册、不可变 scenario steps；
- 每个 attempt 返回固定 success、structured abstain、transient/permanent error、timeout 或 unknown outcome；
- usage/token/cost 由 fixture 明确给出；
- 调用记录使用稳定 operation/attempt ID；
- 未预期调用、调用顺序错误或额外调用立即失败；
- 不读取环境变量，不访问网络，不生成随机响应。

### 14.2 Fake Tools

至少提供：

- 一个 read-only/idempotent 检索类 Fake Tool；
- 一个可模拟 timeout/failure 的 Fake Tool；
- 如测试 unknown outcome，提供一个标记为 non-idempotent 的 side-effect Fake Tool，但不得产生真实外部副作用。

Fake Tool 结果必须使用 B01 合同或明确的测试 adapter 转换为 Source/Evidence candidate，不得绕过身份工厂。

### 14.3 Fake Clock

Fake Clock 可确定性推进：

- provider latency；
- tool latency；
- retry backoff；
- deadline exhaustion。

测试不得等待真实秒数。

## 15. Minimal Deterministic E2E Harness

实现一个仅供可靠性验证的最小 harness，驱动：

```text
已批准 Brief
→ validated Subtask DAG
→ RunState 进入执行
→ Fake provider/tool operations
→ budget/retry/timeout/cancel/replan policies
→ 最小结果/abstention
→ B02 validation/terminal transition
→ events + checkpoints
→ replay/resume 验证
```

它不是正式 Planner/Executor/Writer；不得提前引入完整研究 Prompt 或生成真实报告。

建议 scenario：

1. `success_minimal`：一次检索、一次结构化 provider response、验证后成功；
2. `insufficient_evidence`：检索为空或证据不足，明确 abstain；
3. `transient_retry_success`：第一次 transient，第二次成功；
4. `timeout_exhausted`：operation timeout，有限 retry 后结构化终止；
5. `cancel_before_next_call`：取消后零额外调用；
6. `budget_exhausted`：下一调用前被 ledger 拒绝；
7. `single_replan_success`：一次合法 DAG 替换后成功；
8. `replan_limit_exceeded`：第二次 replan 被拒绝并终止；
9. `unknown_non_idempotent_outcome`：不盲重试；
10. `resume_each_boundary`：在每个 durable event/operation 边界恢复，最终状态、ledger、调用记录与无中断运行一致。

如测试规模需要拆分文件可以变通，但不得省略核心场景。

## 22. 测试要求

### 22.1 Budget/Ledger

- 各维度边界前允许、边界处/超出时拒绝；
- 计数单调；
- reserve/reconcile；
- retry/timeout/失败 attempt 计费；
- 相同 charge replay 不重复；
- resume 后 ledger 与无中断一致；
- 费用不使用 float；
- 运行中不能扩大预算。

### 22.2 Timeout/Cancel/Retry

- FakeClock 无真实等待；
- operation/run deadline；
- timeout 不留下后台任务；
- cancel 前/中/后安全点；
- transient/rate-limit 白名单 retry；
- permanent/contract/grounding/budget/cancel 不 retry；
- unknown non-idempotent outcome 不 retry；
- attempts/backoff 有界；
- budget/deadline 在每次 retry 前重验。

### 22.3 Replan

- 一次合法 replan；
- 新 DAG 校验；
- 不改变历史 completed work/evidence；
- 相同计划拒绝；
- 超过次数拒绝；
- 不重置 ledger/deadline；
- replay 可恢复 replan decision。

### 22.4 Fake E2E

- success；
- insufficient evidence；
- transient retry success；
- retry exhausted；
- timeout；
- cancel；
- budget exhausted；
- single replan success；
- replan exhausted；
- unknown outcome；
- 每个 durable boundary 中断/resume；
- full replay 与 resumed final state/ledger/journal 一致；
- replay 零 provider/tool calls。

### 22.5 边界

- 新模块无真实 provider/Web/LangGraph/旧 agent import；
- 不读取密钥；
- 不写 outputs；
- schema byte drift；
- golden trace 无随机/绝对路径/墙钟漂移；
- 旧 B01/B02 测试全部通过。

测试数量不得预先伪造，应按独立行为组织。
