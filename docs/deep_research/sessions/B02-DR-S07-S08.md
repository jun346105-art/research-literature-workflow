## 1. 唯一目标

在 `src/litflow/deep_research/` 新命名空间中，为 B01 的不可变领域合同建立一个不依赖 LLM、LangGraph、网络或旧 M8 runtime 的确定性运行内核。

1. 研究运行只能沿显式合法边转换；

7. 全部验证只在临时目录运行，不创建新的正式 `outputs/`。

## 5. 四项核心设计原则

### 5.1 事件是状态变化的权威记录

每个成功状态转换必须同时返回：

- 新的不可变 `RunState`；
- 唯一对应的不可变 `RunEvent`。

不得先静默修改状态、之后再“补写日志”。非法转换不得产生事件或部分写入。

### 5.2 Checkpoint 是可丢弃的派生缓存

checkpoint 用于加速恢复，但不能独立证明历史真实性。恢复时必须校验 checkpoint 声明的：

- run identity；
- 已应用事件序号；
- 事件链 head/hash；
- 状态内容或规范序列化 hash。

checkpoint 丢失或落后时，应能从事件流恢复；checkpoint 超前、与事件链冲突或内容被修改时必须 fail closed。

### 5.3 进程中断不是领域状态

不要因为 Python 进程崩溃或机器重启就自动写入虚假的 `crashed` / `paused` 领域状态。恢复应重放到最后一个已完整提交的事件。

timeout、cancel、retry、budget exhaustion 和 controlled replan 的正式语义属于 B03（S09）及之后。本轮不得抢先实现其策略。

### 5.4 确定性与可审计优先

- 相同初始输入和相同事件序列必须恢复出相同语义状态；
- 时间戳可以作为审计元数据，但不得决定 event ID、状态结果或 replay 分支；
- 禁止使用 Python `hash()`、随机数、临时目录或私人绝对路径生成稳定身份；
- JSON 规范化、hash 与换行行为应跨 Windows/Linux 可复现。

## 6. RunState v1

实现严格、不可变、版本化的 Pydantic v2 `RunState`。精确字段命名可以根据 B01 实际合同最小调整，但必须表达：

- schema/runtime version；
- 稳定 `run_id`；
- `task_id`；
- 已批准 brief 的引用或尚未批准的明确状态；
- 当前显式 lifecycle status；
- 已应用事件数量或最后事件序号；
- 最后 event ID / chain head；
- 终态原因的结构化表示（仅在适用时）；
- 状态机恢复所需的最小确定性引用。

要求：

- `extra="forbid"`；
- 不可变；
- 不保存 API key、环境变量值、原始 provider response 或私人绝对路径；
- 不放任意无 schema 的 `dict[str, Any]` 作为通用状态垃圾桶；
- 不把大型全文、passage corpus 或模型上下文复制进 RunState；
- 对 B01 对象只保存稳定引用，不复制并分叉事实对象。

如实现 `run_id` 工厂，必须沿用 B01 identity 规则，并测试稳定性、语义敏感性和路径无关性。

## 7. 显式状态机与 transition guards

### 7.1 状态集合

冻结一个最小 v1 lifecycle，至少覆盖以下语义：

- 新 run 已创建；
- 等待 Brief 审批；
- Brief 已批准、可执行；
- 正在执行研究流程；
- 正在进行最终确定性验证；
- 成功终态；
- 证据不足终态；
- 执行失败终态。

可以根据已冻结架构采用更清晰的枚举命名，但不得添加没有本轮语义与测试支撑的“万能状态”。

本轮不要把 Writer、Web、Critic、Multi-Agent、timeout、retry、cancel 或 replan 伪装成已经实现的状态能力。

### 7.2 转换表

在源码中以单一可检查结构表达允许边，不得将状态转换散落在多个 `if/else` 中。

至少冻结并测试：

- 合法 happy path；
- 证据不足终态；
- 执行失败终态；
- 未批准 Brief 不能进入执行；
- 不允许跳过验证直接成功；
- 终态为 absorbing state；
- 相同状态的无理由 self-transition 被拒绝；
- 任意未列出的边均拒绝。

如 B01 的 `BriefApproval` 已有审批身份/状态，guard 必须使用其程序可验证字段，不能接受调用方传入一个裸 `approved=True` 绕过合同。

### 7.3 纯转换函数

核心转换应是可单测的纯函数或等价确定性 API：

```text
current state + validated transition command/context
    -> next state + event
```

不得在核心转换函数内部：

- 调用 LLM、网络、LangGraph、数据库或系统时间决定分支；
- 写文件后才验证 transition；
- 隐式 retry；
- 自动吞掉异常并返回 success。

## 8. Durable Event v1

实现严格、不可变、版本化的 `RunEvent` 合同。至少包含：

- event schema version；
- 稳定 `event_id`；
- `run_id`；
- 单调、连续的 sequence number；
- event/transition type；
- from/to state；
- 与本次转换相关的最小结构化 payload；
- previous event hash / chain head；
- 当前 event hash；
- 可选审计时间元数据，但其不参与语义决策。

约束：

- event ID 与 event hash 由程序依据 canonical payload、run ID、sequence 和前链信息生成；
- event hash 计算时必须明确定义排除自身 hash 字段；
- 首事件使用显式 genesis 规则；
- payload 必须是已定义的结构化合同或判别联合，禁止任意 JSON dict；
- 不把 prompt、完整模型回答、API key 或私人路径塞入状态转换事件；
- 事件反序列化后必须重新校验 ID/hash，而不是只相信 JSON 中的字符串。

必须区分：

- event identity/hash：用于一致性和篡改检测；
- 安全认证/签名：本项目本轮没有实现。

不得把 SHA-256 hash chain 宣称为密码学签名或访问控制。

## 9. Append-only Event Log

实现一个面向明确文件路径的最小 JSONL event store。生产代码不得硬编码 `outputs/`；测试只传入 `tmp_path`。

要求：

- 每行一个完整 canonical JSON event；
- 固定 UTF-8 与 LF；
- 只允许 append，不提供覆盖历史事件的公共 API；
- append 前校验 run ID、sequence 连续性、previous hash 与当前链 head；
- 对空文件、最后一行完整文件和合法尾部换行有明确行为；
- 发现半行、非法 JSON、未知字段、重复 sequence、缺号、乱序、跨 run 或 hash mismatch 时 fail closed；
- append 已存在的同一 event 不得静默成功，除非明确实现并文档化严格幂等条件；默认应拒绝重复；
- 单进程 crash consistency 要有明确边界；不要声称已经解决多进程并发写入。

如果为保证单事件落盘使用 flush/fsync，应在 Windows 与 Linux 上安全实现并测试可调用性；不得虚构跨文件事务保证。

## 10. Checkpoint v1

实现版本化 checkpoint envelope，至少包含：

- checkpoint schema version；
- run ID；
- 已应用的最后 sequence；
- event chain head；
- RunState 规范序列化内容；
- RunState hash；
- 可选审计元数据。

写入要求：

- 在目标同目录生成临时文件；
- flush/fsync 后以 `os.replace` 原子替换；
- 不在失败时覆盖最后一个已知良好 checkpoint；
- 不使用固定共享临时文件名造成相互踩踏；
- 不把 checkpoint 写入历史 outputs，除非未来另有执行单授权。

读取要求：

- strict schema validation；
- 校验 state hash；
- 校验 run ID、sequence 和 chain head；
- checkpoint 不能引用事件日志中不存在的未来 sequence；
- checkpoint 与相应日志前缀不一致时拒绝。

## 11. Replay 与恢复

提供清晰的 replay API，至少支持：

1. genesis + 完整事件流；
2. genesis + 任意合法事件前缀；
3. 已验证 checkpoint + checkpoint 之后的事件 tail；
4. checkpoint 缺失时退化为全量 replay；
5. checkpoint 落后于事件日志时，从 tail 前进；
6. 空事件流恢复初始 state。

每次 replay 必须重新执行：

- schema 校验；
- run ID 校验；
- sequence 连续性；
- hash chain；
- from-state 与当前状态一致性；
- transition table 与 guard；
- 事件 payload 与状态变化的一致性；
- 最终 state 的 event count / head 一致性。

禁止：

- 直接把最后一个事件的 `to_state` 当作可信最终状态；
- 直接加载 checkpoint 而不核对事件历史；
- replay 时重新调用 provider 或工具；
- replay 时生成新的领域事件；
- 对未知 event type 做 best effort 猜测。

## 12. 写入顺序与崩溃边界

明确采用并记录以下恢复语义：

1. 先在内存完成并验证 transition；
2. append 单个完整 event；
3. event 成功落盘后，再更新 checkpoint；
4. checkpoint 更新失败时，event log 仍是真相，下一次可从旧 checkpoint + tail 恢复；
5. 不允许 checkpoint 已前进但对应 event 不存在。

不要声称两个文件之间实现了通用 ACID transaction。B02 只需证明这一单写者顺序在测试覆盖的 crash windows 下可恢复。

## 15. 测试要求

新增独立专项测试，建议：

`tests/test_deep_research_runtime_kernel.py`

至少覆盖以下类别。

### 15.1 状态与 guard

- 初始状态确定性；
- 全部合法边；
- 全部未列出非法边；
- 未批准 brief 进入执行被拒绝；
- 跳过验证直接成功被拒绝；
- 终态后任何转换被拒绝；
- 非法转换不产生 event、不改变原 state。

### 15.2 事件身份与链

- 相同语义 transition 产生相同 event ID/hash（排除审计时间）；
- payload、sequence、run ID、from/to 任一变化导致 hash 变化；
- genesis 规则；
- JSON round-trip 后重验 ID/hash；
- 篡改 payload、event ID、hash 或 previous hash 被拒绝；
- 重复、缺号、乱序、跨 run 事件被拒绝。

### 15.3 Event store

- 多事件 append/read；
- UTF-8/LF 与 canonical JSON；
- 半行、坏 JSON、未知字段被拒绝；
- 失败 append 不破坏此前合法前缀；
- 只在 `tmp_path` 写入。

### 15.4 Checkpoint

- 原子写入与 round-trip；
- checkpoint state hash 篡改被拒绝；
- run ID/sequence/head mismatch 被拒绝；
- checkpoint 落后时可从 tail 恢复；
- checkpoint 超前或引用不存在事件被拒绝；
- 模拟 replace 前失败时保留旧良好 checkpoint（可通过注入/monkeypatch，不做不稳定的真实断电测试）。

### 15.5 Replay

- 对一条代表性合法 run 的每一个事件前缀逐一 replay；
- 每个前缀结果等于逐步 transition 结果；
- full replay 与 checkpoint+tail 结果相同；
- replay 不产生新事件、不执行外部调用；
- tamper/reorder/gap/duplicate/cross-run 全部 fail closed；
- terminal result 可重放且不可继续转换。

### 15.6 边界测试

- 新模块不得 import `litflow.agent`、LangGraph、provider/Web client；
- 不依赖 M8 outputs；
- 不访问真实 `outputs/`；
- 稳定 schema 导出无 drift；
- Windows 路径不进入 durable identity/artifact。

专项测试数量不预先伪造。测试应按行为边界组织，避免为了增加数字拆成无意义断言。

## 21. 完成门槛

只有同时满足以下条件才可判定 B02 `pass`：

- RunState v1 严格、不可变、版本化；
- 转换表集中定义，所有非法边 fail closed；
- 未批准 Brief 不能进入执行；
- 终态不可继续转换；
- transition 原子地产生 next state + event；
- RunEvent 有连续 sequence、程序拥有 ID 与可验证 hash chain；
- JSONL store 只追加并拒绝损坏、乱序、重复与跨 run；
- checkpoint 原子写入、内容和链 head 可校验；
- full replay、所有合法前缀 replay、checkpoint+tail replay 一致；
- checkpoint stale 可恢复，checkpoint ahead/mismatch 被拒绝；
- 新内核不依赖旧 M8、LangGraph、provider 或 outputs；
- runtime JSON Schema 稳定导出；
- 专项与全量测试全部通过；
- 文档、Session Log、Traceability Matrix 已更新；
- commit/push 成功且工作树 clean；
- 历史 outputs、M8、MVP 和 tag 未修改。

以下情况只能判定 `blocked` 或 `fail`：

- 只定义 enum，没有可验证 guards；
- 只把状态写 JSON，没有事件链；
- checkpoint 被当成唯一真相且不核验事件历史；
- replay 只是读取最后一条事件的 `to_state`；
- 任意损坏事件被跳过或猜测修复；
- 依赖旧 M8 runtime 或历史 outputs；
- 为通过测试放宽 B01 合同或旧 validator；
- 运行了未经授权的外部调用；
- 工作树或 tag 身份不符合要求。
