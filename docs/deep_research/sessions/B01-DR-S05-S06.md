## 7. 通用合同规则

### 7.1 Strict base model

所有持久化合同必须：

- `extra="forbid"`；
- 自动strip普通字符串或通过显式validator规范；
- 对空字符串、空白ID、NaN/Infinity等无效值fail closed；
- 使用timezone-aware UTC datetime；
- JSON可序列化、可round-trip；
- 合同版本显式，例如 `dr-contracts-v1`；
- 字段有description，生成Schema不依赖内部实现注释。

是否使用 `frozen=True` 应按领域语义决定：身份与Evidence等持久化事实对象应不可变；Brief draft等若需要演进，应通过创建新版本而不是原地静默修改。必须在文档说明。

### 7.2 稳定ID

`identity.py` 必须提供程序端工厂：

- canonical JSON：稳定key排序、UTF-8、明确分隔符；
- SHA-256；
- 类型前缀，例如 task/brief/subtask/source/evidence/claim/citation；
- 同一规范化输入生成同一ID；
- 语义输入变化生成不同ID；
- 时间戳、绝对路径、随机数、Python hash不得进入确定性ID；
- 不把截断hash描述为安全认证机制。

完整hash或截断长度由实现选择，但需记录碰撞考虑并用测试冻结格式。

### 7.3 程序所有权

模型用于持久化/replay时可以解析已有ID，但新对象的生产路径必须通过程序工厂。不得把“模型输出一个字符串ID”作为权威身份来源。

B01只实现合同与工厂，不实现模型输出转换器。

## 8. Task / Brief / Subtask合同

### 8.1 ResearchTask

至少表达：

- contract_version；
- task_id；
- original_question；
- language/locale；
- created_at；
- 用户约束或边界；
- 期望交付类型。

禁止存API key、模型配置、私人绝对路径。

### 8.2 ResearchBrief

至少表达：

- brief_id与task_id；
- objective；
- scope inclusions/exclusions；
- deliverable；
- success criteria；
- constraints；
- approval状态与独立 `BriefApproval` 记录。

Approval至少能区分draft/approved/rejected，并记录批准主体和UTC时间；不得使用一个无法审计的裸布尔值代替完整审批语义。

本轮不实现“未批准禁止执行”的runtime guard，但合同与测试必须支持后续guard。

### 8.3 ResearchSubtask

至少表达：

- subtask_id、task_id；
- question/objective；
- rationale；
- dependency IDs；
- expected evidence；
- completion criteria。

不包含worker/agent名称、执行状态、重试次数或预算消耗；这些属于S07–S10。

Subtask集合必须能检查：

- ID唯一；
- dependency存在；
- 禁止self dependency；
- 禁止cycle；
- stable topological order或明确只校验DAG。

## 9. Source / Evidence / Claim / Citation合同

### 9.1 Source

至少表达：

- source_id；
- source kind（当前local PDF/已有语料，预留未来Web但不实现抓取）；
- canonical reference；
- title与可选bibliographic metadata；
- content SHA-256或等价内容身份；
- language与时间信息（如适用）。

持久化canonical reference不得是Windows/Linux私人绝对路径。可使用Zotero key、DOI、规范URL、paper key、内容hash或其他可迁移标识。

### 9.2 EvidenceLocator

需统一支持当前文本证据和未来page/region扩展，至少可表达：

- passage/chunk identity；
- page number（1-based，如适用）；
- text span start/end（成对出现且范围合法）；
- 可选region/bbox与coordinate-space元数据；
- locator不适用的字段必须为空并通过modality约束。

不要实现图像裁剪、OCR或VLM。bbox合同只为未来版本兼容，并明确当前为planned capability。

### 9.3 EvidenceUnit

至少表达：

- evidence_id与source_id；
- modality；
- locator；
- verbatim/groundable content；
- content hash；
- language；
- provenance metadata的受控字段。

不得把模型自由摘要当作原文Evidence；派生解释必须与verbatim证据分开。

### 9.4 Claim

至少表达：

- claim_id与task_id；
- claim text；
- language；
- 可选实体或claim type；
- 不在Claim内部嵌入任意citation对象。

Claim是否可展示由后续Validator决定，本轮不能增加“validated=true”默认值冒充通过。

### 9.5 Citation

至少表达：

- citation_id；
- claim_id与evidence_id；
- relation：support/contradict/context或经证据确定的最小集合；
- 可选quote/span引用；
- 不复制或修改source identity。

Citation必须引用已存在的Claim和Evidence；quote/span若存在，必须能在Evidence内容内被程序校验。语义支持正确性留给后续评测，不能由字段名称假定。

## 10. 跨对象Bundle不变量

实现一个明确的聚合合同或验证入口，至少检查：

- Brief与所有Subtask/Claim属于同一Task；
- Evidence引用存在的Source；
- Citation引用存在的Claim和Evidence；
- 所有ID在各自集合唯一；
- Subtask dependency DAG合法；
- quote/span范围合法且与Evidence文本一致；
- content SHA-256与持久化内容一致；
- locator modality约束成立；
- JSON round-trip后身份与内容不变。

不要在B01检查provider调用、预算、状态转移、最终报告coverage或跨claim逻辑矛盾。

- UTF-8、稳定排序、固定缩进和末尾换行；

- 不在测试中覆盖仓库文件；
- Schema不得包含本机路径、时间戳或不稳定定义顺序。

如果Pydantic生成内容存在合理的跨版本非确定性，应先归一化而不是放弃drift test；无法稳定时停止并报告。
